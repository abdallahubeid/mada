EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Five sequential tasks, each building on the last. The sidebar was made
role-aware. A Task/Scrum module was built end-to-end. Dashboards were split
three ways and the notification system — which had silently delivered to
Owners only — was rebuilt to route by permission. The My Space hub was
retired in favour of four first-class self-service routes. Finally, every
data table in the tenant app was brought under one markup contract, which
surfaced and fixed a real RTL alignment bug.

Two findings changed the shape of the work. First, `TenantOwnerNotifier`
hard-filtered every one of the app's 15 notifications to Owners, so an HR
Manager received nothing at all — not even the leave requests they are
responsible for approving. Second, table columns appeared misaligned not
because of missing CSS classes but because `dir="ltr"` on a `<td>` silently
flips what the logical `text-start` resolves to.

Both were diagnosed by measurement, not inspection.

01 - ROLE-AWARE SIDEBAR NAVIGATION
================================================================================
Goal: Owner sees HR collapsed into one dropdown; HR Manager sees the same
pages flat; employees get a flat self-service section.

APPROACH
  The existing render loop already supported both shapes — flat items and
  dropdown-with-children (used by the Access & Permissions group). No new
  markup was needed. The nine HR items were extracted to $hrManagementItems
  and the group's *shape* is branched once, up front:

    @hasrole('Owner')  ->  $hrGroup = [ 'children' => $hrManagementItems ]
    otherwise          ->  $hrGroup = [ 'items'    => $hrManagementItems ]

CARRY-OVER BUG GUARD
  `@hasrole` calls hasRole() with no cleanup, caching the `roles` relation
  scoped to the team id active at that moment. Left cached, the next
  Gate-driven @can (which runs Gate::before -> isPlatformSuperAdmin() ->
  isTenantOwner(), both team-switching) would reuse it via a no-op
  loadMissing() — the exact stale-cache class of bug fixed at source in the
  previous session. A defensive `auth()->user()?->unsetRelation('roles')`
  was added immediately after the @hasrole block.

03 - ROLE-SPECIFIC DASHBOARDS + ROLE-AWARE NOTIFICATIONS

Ran as a two-phase task: a read-only analysis phase delivered for approval,

--------------------------------------------------------------------------------
3.1  PHASE 1 - FINDINGS THAT CHANGED THE BRIEF
--------------------------------------------------------------------------------
(1) THERE IS NO PAYROLL MODULE.
    Zero tables, zero models, zero controllers. EmployeeContract is
    explicitly docblocked "(non-payroll)" and carries no salary field.
    All payroll widgets were struck from scope.

(2) THERE IS NO birth_date COLUMN.
    The requested "upcoming birthdays" widget was not buildable. Work
    anniversaries derived from joining_date shipped instead (approved).

(3) EVERY NOTIFICATION WAS OWNER-ONLY.
    TenantOwnerNotifier::ownersForTenant() hard-filters ->role(ROLE_OWNER).
    All 15 notifications routed through it. An HR Manager received nothing.

    The delivery half of the stack was already role-neutral and needed no
    change: NotificationController uses $user->notifications(), the Reverb
    channel is per-user (tenant.{tenantId}.notifications.{userId}), and
    TenantNotificationChannel authorizes any user on their own channel.
    Only the fan-out layer was hardcoded.

(4) ANNOUNCEMENTS PERMISSION GAP.
    tenant.announcements.view_any was granted only to HR Manager + Owner —
    a standard Employee could not read ANY announcement, including urgent
    ones. A read-only self-service grant was added.

APPROVED DECISIONS (all four "Recommended")
  - Work anniversaries only (no birth_date migration)
  - Smart dispatcher on /dashboard (not separate routes + login redirect)
  - HR task widget scoped org-wide
  - Rename TenantOwnerNotification -> TenantNotification

--------------------------------------------------------------------------------
3.2  NOTIFICATION ARCHITECTURE REBUILD
--------------------------------------------------------------------------------
  [RENAME] TenantOwnerNotification -> TenantNotification
           14 subclasses updated mechanically.

  [NEW] Services/Tenancy/TenantNotifier.php
        toOwners() / toRole() / toPermission() / toEmployee() /
        toLineManagerOf() / toAllStaff() / toUsers()
        Every resolver binds the tenant as Spatie's permission team id and
        restores it in a finally block, then unsets the cached `roles`
        relation — same discipline as User::isTenantOwner().

  [KEEP] TenantOwnerNotifier — now a thin delegating wrapper, so all 15
         existing call sites work untouched.

  THE DOUBLE-DELIVERY PROBLEM
    Rather than rewrite the Owner listeners (risk, and their names would
    start lying), a parallel listener was added:

      NotifyOwnersOf*            (untouched)  -> Owners
      NotifyHrOfOperationalEvents (new)       -> permission holders, minus Owners

    Recipients resolve by PERMISSION, not role name, so custom tenant roles
    holding the ability are included automatically. All 9 call sites pass
    `includeOwners: false` — without it a user holding both Owner and HR
    Manager receives every notification twice.

    This guard is covered by a test that was VERIFIED TO FAIL when the flag
    is flipped (asserts 1 sent, gets 2). A test that cannot fail is worthless.

  NEW EVENTS
    TaskAssigned, TaskCompleted, LeaveRequestDecided, EvaluationPublished

  NEW NOTIFICATIONS
    TaskAssignedNotification, TaskCompletedNotification,
    LeaveDecisionNotification, EvaluationPublishedNotification,
    CheckOutReminderNotification

  TRANSITION GUARDS (each fires once, on the real state change)
    - Task completion  : only on the transition INTO Completed
    - Evaluation       : only on the draft -> visible transition; approve()
                         captures draft ids BEFORE the mass update overwrites
                         status, since ->update() fires no model events
    - Leave            : only on a terminal decision; an escalation to the
                         next approval level leaves it pending and is silent

  NOTE: LeaveController::approve()/reject() previously fired NO events at
  all — only audit logs. Employees were never told the outcome of their own
  leave request.

  SCHEDULED
    tenant:send-check-out-reminders — weekdays 18:30, idempotent per
    employee per day via Cache::add expiring at midnight (matches the
    existing expiring-contract command pattern).

3.3  DASHBOARDS
--------------------------------------------------------------------------------
  DISPATCHER
    /app/dashboard stays the single post-login destination and routes by
    role. Owner falls through to the executive dashboard rendered in place;
    HR Manager and Employee redirect to their own bookmarkable URLs.

    Owner is checked FIRST — Owners hold every permission through the
    Gate::before bypass, so a permission-first ordering would route them to
    the HR dashboard.

  THE ABSENCE GAP  (worth knowing about)
    AttendanceStatus::Absent only exists when someone explicitly recorded
    it. An employee who simply never checked in has NO ROW AT ALL and is
    invisible to a `where(status, Absent)` count. HrDashboard therefore
    computes a third bucket:

      no_record = active headcount - employees with any row today

    and counts both toward the absence rate. This is why the existing
    ExecutiveDashboard attendance rate can read misleadingly high.
    Verified live: 3 employees, 1 present, 1 late, 1 no-record -> 33.3%.

  HR DASHBOARD (tenant.hr.dashboard, permission hr.dashboard.view)
    KPIs: headcount, present today, absence rate, pending leaves
    Attendance split incl. the no_record bucket
    Pending leave approval queue
    Evaluation progress for the org's configured period
    Org-wide task rollup + overdue (excludes completed-but-past-due)
    Contract renewals (30d), probation endings (30d) [previously unused],
    on-leave-today roster, work anniversaries (30d)

  EMPLOYEE DASHBOARD (tenant.hr.employee.dashboard, hr.my_dashboard.view)
    Deliberately a SUMMARY, not a second My Space — deep-links into the
    existing surfaces rather than duplicating their history tables.
    Today's attendance + check-in/out CTA, Scrum summary + overdue + next
    due, leave balances, latest evaluation (Submitted/Approved only — Draft
    is the evaluator's private copy), pending leaves, month attendance,
    contract, assigned assets, announcements.

  REGRESSIONS FIXED
    The dispatcher broke 3 existing tests that asserted 200 on /app/dashboard
    for non-Owners. Fixed with followingRedirects() — preserving intent
    ("this role is not denied"), not weakening the assertion.

05 - SYSTEM-WIDE DATA TABLE STANDARD
================================================================================
--------------------------------------------------------------------------------
5.1  THE ALIGNMENT BUG - ROOT CAUSE
--------------------------------------------------------------------------------
Not missing classes. Measured in the browser on my-attendance:

  column          header inset    cell inset     drift
  --------------  ------------    -----------    --------
  #                     16px           16px      aligned
  التاريخ                16px          185px      169px
  حضور                  16px          127px      111px
  انصراف                16px          149px      133px
  الحالة                 16px           16px      aligned

Cells WITHOUT dir="ltr" aligned perfectly. Cells WITH it drifted.

getComputedStyle reported `text-align: start` on BOTH the <th> and the <td>
— which is exactly why this looked like a class problem. But `start`
resolves against each element's OWN direction: left inside a dir="ltr" cell,
right inside the RTL header. Same class string, opposite physical edge.

FIX
  dir="ltr" moved off the cell onto an inner <x-ui.ltr> span. The cell stays
  RTL so header and value share one edge; digits still render in reading
  order (2026-08-04, not reversed). Re-measured: all columns at 16px.

--------------------------------------------------------------------------------
5.2  WHAT WAS APPLIED
--------------------------------------------------------------------------------
  Scope: 29 tables across 23 tenant views.
  Excluded: 4 reports/print/* views — standalone HTML with inline CSS and no
  Tailwind. They already had # and explicit text-align: right, and were
  never affected by the bug.

  status/action columns centred ...... 32  (header AND cell moved together)

--------------------------------------------------------------------------------
5.3  FOUR JUDGMENT CALLS
--------------------------------------------------------------------------------
(1) THE SPECIFIED slate-* CLASSES WERE NOT USED.
    `bg-slate-800/50` + `text-slate-200` assume a dark-only design. This app
    defaults to LIGHT mode with dark opt-in via an explicit .dark class
    (ADR-15). Applied literally, all 29 tables would get a dark header bar
    and near-white text on a #fafafa page. The exact typography SCALE was
    implemented using the project's ink/mist tokens with light+dark pairs.
    Verified rendering: 12px / 600 / uppercase / 0.6px tracking; thead
    #f4f6f5 in light, #081425 in dark.

(2) SIX TABLES ALREADY HAD BETTER INDEXING THAN $loop->iteration.
    They carry the page offset so numbering stays continuous across pages.
    These were PRESERVED, not downgraded, and offset-carrying is now the
    documented rule for paginated tables.

(3) TRASH KEEPS ITS CHECKBOX IN COLUMN 1.
    It is a selection control, not data. # follows it.

(4) ONE TABLE HAS NO # COLUMN BY DESIGN.
    The audit-log field-diff panel compares before/after values for a single
    record via Alpine x-for. No row sequence to number, no Blade $loop.

--------------------------------------------------------------------------------
5.4  A NEAR-MISS WORTH RECORDING
--------------------------------------------------------------------------------
The action-column centring initially used a global `flex justify-end` ->
`justify-center` replace. A check before applying showed only 5 of 14
occurrences were inside tables — the other 9 were FORM FOOTERS (Cancel /
Save button rows) across 9 files. The replacement was scoped to table blocks
only; form footers verified unchanged.
